Q: একটি API আগে ২ সেকেন্ডে Response দিত, কিন্তু হঠাৎ করে কোনো Code Change ছাড়াই ২ মিনিট (১২০ সেকেন্ড) সময় নিতে শুরু করেছে। কীভাবে সমস্যাটি
Diagnose করা হবে? সম্ভাব্য কারণগুলো কী হতে পারে?

-> সম্ভাব্য কারণসমূহ
1. ডাটাবেস কোয়েরি এবং ইনডেক্সিং সমস্যা (সবচেয়ে সাধারণ)
- ডেটা বৃদ্ধি: এক সপ্তাহ আগে টেবিলে ডেটা কম ছিল, তাই দ্রুত কাজ করত। এখন ডেটা অনেক বেড়ে যাওয়ায় ডাটাবেস পুরো টেবিল স্ক্যান (Full Table Scan) করছে। সঠিক ইনডেক্স (Index) না থাকলে এমন হয়।

- N+1 কোয়েরি সমস্যা: জ্যাঙ্গো ওআরএম (Django ORM)-এ রিলেশনাল ডেটা আনার সময় select_related() বা prefetch_related() ব্যবহার না করলে লুপের ভেতর বারবার ডাটাবেস হিট হয়।

- ডাটাবেস লক (Database Locks): অন্য কোনো ব্যাকগ্রাউন্ড টাস্ক (যেমন Celery) বা কোয়েরি যদি ডাটাবেসের কোনো টেবিল লক করে রাখে, তবে আপনার এপিআই সেই ডেটা পড়ার জন্য দীর্ঘক্ষণ অপেক্ষা করতে পারে।

2. থার্ড-পার্টি সার্ভিসে টাইমআউট (Third-Party API Timeout)
আপনার এপিআই কি অন্য কোনো এক্সটার্নাল এপিআই (যেমন: পেমেন্ট গেটওয়ে, এসএমএস সার্ভিস) কল করছে?

যদি সেই এক্সটার্নাল সার্ভিসটি ডাউন বা ধীরগতির হয়, তবে আপনার কোড সেখানে আটকে থাকবে।

পাইথনের requests লাইব্রেরিতে বাই-ডিফল্ট কোনো টাইমআউট থাকে না। তাই থার্ড-পার্টি এপিআই রেসপন্স না দিলে আপনার কোড অনন্তকাল বা সার্ভার টাইমআউট হওয়া পর্যন্ত অপেক্ষা করবে (যা সাধারণত ১২০ সেকেন্ড বা ২ মিনিট হয়ে থাকে)।

3. ফাস্টএপিআই (FastAPI) ইভেন্ট লুপ ব্লক হওয়া
আপনি যদি ফাস্টএপিআই (FastAPI) ব্যবহার করেন, তবে async def ফাংশনের ভেতরে কোনো সিঙ্ক্রোনাস (Synchronous) কাজ (যেমন: সাধারণ requests.get(), ভারী ক্যালকুলেশন বা সিঙ্ক্রোনাস ডাটাবেস কোয়েরি) করলে তা পুরো ইভেন্ট লুপকে ব্লক করে দেয়। এর ফলে অন্যান্য রিকোয়েস্টও আটকে যায় এবং রেসপন্স টাইম মারাত্মকভাবে বেড়ে যায়।

4. সার্ভারের রিসোর্স শেষ হয়ে যাওয়া (Resource Exhaustion)
RAM বা CPU ওভারলোড: সার্ভারে মেমরি লিক (Memory Leak) হলে র‍্যাম ফুল হয়ে যেতে পারে। তখন সার্ভার হার্ডডিস্কের 'সোয়াপ মেমরি (Swap Memory)' ব্যবহার শুরু করে, যা খুবই ধীরগতির।

ওয়ার্কার (Worker) শেষ হয়ে যাওয়া: Gunicorn বা Uvicorn-এর সবগুলো ওয়ার্কার যদি আগের কোনো রিকোয়েস্ট প্রসেস করতে গিয়ে আটকে থাকে, তবে নতুন রিকোয়েস্টগুলো কিউ (Queue)-তে পড়ে থাকে।


-> কীভাবে ডায়াগনস্টিক বা ট্রাবলশুট করবেন? (How to Diagnose)
সমস্যাটি ঠিক কোথায় হচ্ছে তা ধরার জন্য নিচের পদক্ষেপগুলো অনুসরণ করুন:

ধাপ ১: লগ (Logs) চেক করা
সবার আগে Nginx এবং Gunicorn/Uvicorn-এর লগ চেক করুন।

Nginx-এর access.log এবং error.log দেখে নিশ্চিত হোন যে রিকোয়েস্টটি ওয়েবস সার্ভার থেকে পাইথন প্রজেক্ট পর্যন্ত পৌঁছাতে কত সময় নিচ্ছে।

যদি Nginx-এ 504 Gateway Timeout বা 502 Bad Gateway দেখেন, তার মানে আপনার পাইথন অ্যাপ্লিকেশন নির্দিষ্ট সময়ের মাঝে রেসপন্স করতে ব্যর্থ হয়েছে।

ধাপ ২: পাইথন কোডে সময় পরিমাপ করা (Execution Time Tracking)
এপিআই-এর কোন অংশটি সময় নিচ্ছে তা বের করতে কোডের বিভিন্ন অংশে সময় মেপে (Time Profiling) দেখতে হবে।

Python
import time
import logging

logger = logging.getLogger(__name__)

def my_slow_api_view(request):
    start_time = time.time()

    # আপনার কোডের প্রথম অংশ (ধরা যাক ডাটাবেস কোয়েরি)
    data = fetch_data_from_db()
    logger.info(f"DB Query took: {time.time() - start_time} seconds")

    # দ্বিতীয় অংশ (এক্সটার্নাল এপিআই কল)
    step2_time = time.time()
    call_third_party_api()
    logger.info(f"3rd party API took: {time.time() - step2_time} seconds")

    logger.info(f"Total time: {time.time() - start_time} seconds")
    return Response(data)
লগ ফাইল দেখলে আপনি সহজেই বুঝতে পারবেন ডাটাবেস, থার্ড-পার্টি এপিআই, নাকি আপনার নিজস্ব ক্যালকুলেশন—কোথায় ২ মিনিট সময় নষ্ট হচ্ছে।

ধাপ ৩: ডাটাবেস প্রোফাইলিং
জ্যাঙ্গোর ক্ষেত্রে: লোকাল পরিবেশে django-debug-toolbar ব্যবহার করুন অথবা Django Silk ইনস্টল করে দেখুন ঠিক কোন কোয়েরিটি সবচেয়ে বেশি সময় নিচ্ছে এবং কতগুলো কোয়েরি এক্সিকিউট হচ্ছে।

সরাসরি ডাটাবেসে (MySQL/PostgreSQL) Slow Query Log চালু করে দেখুন ২ সেকেন্ডের বেশি সময় নিচ্ছে এমন কোনো কোয়েরি আছে কিনা।

ধাপ ৪: থার্ড-পার্টি এপিআই কলে টাইমআউট বসানো
যদি আপনার কোডে কোনো requests.get() বা httpx.get() থাকে, তবে অবশ্যই সেখানে একটি হার্ড টাইমআউট দিয়ে দিন।

Python
import requests

try:
    # ৫ সেকেন্ডের বেশি সময় নিলে কোডটি টাইমআউট হয়ে যাবে
    response = requests.get("https://external-api.com/data", timeout=5.0)

ধাপ ৫: সার্ভার মনিটরিং
লুকানো কোনো ইনফ্রাস্ট্রাকচার সমস্যা আছে কিনা তা দেখতে লিনাক্স সার্ভারে ঢুকে htop কমান্ড রান করুন। দেখুন সার্ভারের সিপিইউ (CPU) বা র‍্যাম (RAM) ব্যবহারের হার ১০০% এ পৌঁছেছে কিনা।
