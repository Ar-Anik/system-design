-> Monolithic Architecture Vs Microservices Architecture
Monolithic Architecture-এ একটি Request সাধারণত একই Process-এর মধ্যে অনেকগুলো operation সম্পন্ন করে।

                        Monolithic Application
                               │
                               ▼
                         ┌─────────────┐
    User ───────────────►│ Application │
                         │             │
                         │ Order       │
                         │ Payment     │
                         │ Inventory   │
                         │ Database    │
                         └─────────────┘

এখানে Debugging তুলনামূলকভাবে সহজ হতে পারে, কারণ একই Application Process-এর মধ্যে বিভিন্ন operation-এর Log পাওয়া যায়। কিন্তু Microservices Architecture-এ
একই Request বিভিন্ন Process এবং Host-এর মধ্যে চলাচল করে:

    User
     │
     ▼
    API Gateway
     │
     ▼
    Order Service
     │
     ├────────► Inventory Service
     │
     ├────────► Payment Service
     │
     └────────► Notification Service

প্রতিটি Service-এর নিজস্ব:
- Process
- Container
- Server
- Log
- Database connection
- Network communication
থাকতে পারে।

ফলে শুধুমাত্র Log ব্যবহার করে একটি Request-এর সম্পূর্ণ Journey Reorganization করা কঠিন হয়ে যায়। Distributed Tracing এই সমস্যার সমাধান করে।



Microservices Architecture ব্যবহার করার ফলে System scalability বৃদ্ধি পায় এবং independent deployment অত্যন্ত সহজ হয়। কিন্তু এর একটি বড় অসুবিধা হলো, একটি Request-এর
execution অনেকগুলো independent component-এর মধ্যে ছড়িয়ে যায়। ফলস্বরূপ, System Observability অত্যন্ত complex হয়ে পড়ে।

1. End-to-End System Visibility
একটি User Request ঠিক কোথা থেকে শুরু হয়েছে এবং কোন কোন Service হয়ে শেষ গন্তব্যে পৌঁছায়, তা স্পষ্টভাবে দেখার জন্য Distributed Tracing প্রয়োজন।
একটি Trace-এর মাধ্যমে পুরো Flow একসাথে দেখা যায়। যেমন:

    User Request [Trace ID: x7y8z9a1] (Total Time: 2.1s)
         ↓
    API Gateway [2.1s] (Status: HTTP 200 OK)
         │
         └──> Order Service (Main Orchestrator) [2.0s] (Span ID: 101)
              │
              ├──> [Parallel Execution Starts]
              │    │
              │    ├──> Inventory Service (stock check) [150ms] (Span ID: 102)
              │    │    └──> Inventory Database [50ms] (Span ID: 103)
              │    │
              │    └──> Payment Service (payment process) [1.8s] (Span ID: 104)
              │         ├──> Payment Database (payment record save) [100ms] (Span ID: 105)
              │         └──> External Payment API [1.6s] (Span ID: 106) (⚠️ Latency Bottleneck)
              │
              └──> [Sequential Execution Starts] (উপরের দুটি কাজ সফলভাবে শেষ হওয়ার পর)
                   │
                   └──> Order Database (Confirm order to save) [50ms] (Span ID: 107)

 এই End-to-End Visibility থাকার কারণে System-এর ভেতরের কাজের interaction অত্যন্ত সহজে বোঝা যায়।


 2. Latency & Performance Bottleneck Identification
কোনো Service, Database Query বা External API Call-এ অতিরিক্ত সময় ব্যয় হচ্ছে কি না, তা মিলিসেকেন্ড লেভেলে পরিমাপ করার জন্য Distributed Tracing ব্যবহৃত হয়।
ধরা যাক, একটি Request সম্পূর্ণ হতে মোট সময় লেগেছে 4 seconds:

- Gateway = 20 ms
- Order = 100 ms
- Inventory = 80 ms
- Payment = 3.7 sec
- Notification = 50 ms

এখানে স্পষ্টভাবে দৃশ্যমান যে, Payment Service হলো Primary bottleneck। অর্থাৎ পুরো Application-এর performance problem খুঁজতে প্রতিটি Service-এর Log আলাদাভাবে পরীক্ষা করার প্রয়োজন আর থাকে না।


3. Root Cause Analysis (RCA)
System-এ 500 Internal Server Error বা কোনো Failure ঘটে থাকলে, ঠিক কোন Service-এর কোন লাইন বা অপারেশনে Exception raise করছে তা দ্রুত বের করা অত্যন্ত জরুরি।
উদাহরণস্বরূপ, User-এর request successfully complete না হয় যদি একটি HTTP 500 Internal Server Error পায়, তবে API Gateway-এর Log হয়তো শুধু 500 Internal Server Error দেখাবে। কিন্তু Trace
পরীক্ষা করলে আসল ঘটনাটি বের হয়ে আসে:

    API Gateway (500 Error)
        │
        ▼
    Order Service
        │
        ▼
    Payment Service
        │
        ▼
    Payment Database
        │
        X
        └── Timeout

এখান থেকে নিশ্চিতভাবে বোঝা যায় যে, User-request failure-এর মূল কারণ (Root cause) হলো downstream Database operation-এ ঘটা Timeout। Distributed Systems Debugging-এর জন্য এটি অপরিহার্য।


4. Identifying Cascading Failure
একটি Downstream Service slow হলে কীভাবে তা Upstream Service-গুলোতে delay তৈরি করে, তা Trace দৃশ্যমান করে। ধরা যাক:

    Payment Service
          ↓
    Database
          ↓
    Slow Query
          ↓
    Payment Service becomes slow
          ↓
    Order Service waits
          ↓
    API Gateway waits
          ↓
    User Request becomes slow

Distributed Trace এই dependency এবং latency propagation দৃশ্যমান করতে পারে। উদাহরণ:

API Gateway       ███████████████████████  5s
       │
       └── Order  ██████████████████████   4.8s
                    │
                    └── Payment █████████  4.5s
                                  │
                                  └── DB ███ 4.2s

এখানে দেখা যাচ্ছে downstream Database-এর latency কীভাবে upstream Service-গুলোতে propagate হয়েছে।


5. Identifying Database and External API Issues
Distributed Tracing শুধুমাত্র Service-to-Service HTTP Request-এর মধ্যেই সীমাবদ্ধ নয়। একটি Span একটি Database operation, RPC call, Messaging operation
বা অন্যান্য যেকোনো Operation-কেও represent করতে পারে। উদাহরণ:

    Order Service
    │
    ├── Validate Order (10 ms)
    │
    ├── PostgreSQL Query (1.8 sec)
    │
    ├── Redis Lookup (15 ms)
    │
    ├── Inventory API (50 ms)
    │
    └── Payment API (120 ms)

এখানে যদি Database-এ কোনো সমস্যা থাকে, তবে PostgreSQL Query-এর 1.8 sec সময় লাগার বিষয়টি Trace-এর মাধ্যমে খুব সহজেই শনাক্ত করা সম্ভব হয়।


6. Identifying Unoptimized Calls and N+1 Query Problems
অপ্রয়োজনীয় Repeat DB Queries (N+1 Query Problem) বা একাধিক redundant HTTP Call চিহ্নিত করা Distributed Tracing-এর অন্যতম বড় সুবিধা।
ধরা যাক, একটি Request-এর সময় বারবার একই ধরনের Database operation হচ্ছে:

SELECT orders ...
SELECT product ...
SELECT product ...
SELECT product ...
SELECT product ...

Trace-এ এই repetitive operations দৃশ্যমান হলে N+1 Query Problem Identifying করা অত্যন্ত সহজ হয়ে যায়। এর ফলে Application অপ্রয়োজনীয়ভাবে কতবার Database-এ Call
করছে তা বোঝা যায় এবং তা optimize করা সম্ভব হয়।


7. Dependency Mapping
Service-গুলোর মধ্যকার internal Service Dependencies Automatic ভাবে Mapping করা সম্ভব হয়, যা বড় Architecture বোঝার জন্য অত্যন্ত সহায়ক।


8. Needle in a Haystack
কোনো Error হলে ডজন ডজন Server-এর Log File-এর মধ্যে Manually Log filter করার প্রয়োজন পড়ে না। নির্দিষ্ট Trace ID ব্যবহার করে সরাসরি ঐ নির্দিষ্ট Error বা Exception-টি খুঁজে বের করা সম্ভব হয়।
